# Saved PDF readability

Implemented on `codex/resume-readability`, 2026-10-26. This checks text extraction from the actual saved PDF without a job description or AI request. It is separate from the JD-based Job fit score. It does not measure writing quality or guarantee acceptance by an employer's ATS.

## User flow

Improve opens with two keyboard-accessible tabs: Readability and Job fit. Readability is selected first. Opening it only retrieves an existing check; it never renders a PDF or starts a provider call automatically. Desktop keeps the resume beside the panel. Tablet/phone retains the existing one-task surface and Write/Preview navigation.

1. For a new or changed resume, use Save resume / Save changes. Saving captures a version and does not automatically run a check.
2. Check readability examines that clean saved version. Loading, conflicts and unavailable/error states never show a passing result.
3. The result shows Text recovered in order or measured issues with section names and exact source excerpts. At most three issue groups lead; the rest are available in the preview. Edit resume / Review layout returns to the relevant editor task.
4. View extracted text opens the existing shared dialog, with real page navigation, readable text and bounded inner scrolling. The preview renders plain text, never HTML. Closing restores focus. Changing versions closes the preview and invalidates the old result.

Job fit retains the existing JD assessment, evidence and tailoring flow. Hover Improve with AI, direct edit/move/delete icons, document saving and printable appearance are unchanged. Shared Studio colors, typography, Performative adapters, quiet motion and focus handling remain.

## Measurement

The existing isolated PDF worker renders the same immutable EditorDocument used by saved PDF download. `pdfjs-dist` extracts geometric reading rows from those generated bytes. The independent expected-content projection selects visible saved header/contact values, headings, rich text, entries, bullets, skills and languages. Empty/hidden content and annotation-only link destinations are excluded. No OCR, upload parser heuristic, provider or external font/network request is used.

Normalization tolerates presentation whitespace, case and Unicode compatibility forms; significant `+`, `#` and `%` tokens remain. Text occurrences are consumed, so repeated source text needs repeated extracted occurrences. Metadata within one entry/header group may read in either order; prose and section groups retain ordering. Missing tokens produce missing_text; recovered words in unexpected order produce reading_order. Empty extraction produces no_text. Scattered words are flagged for review rather than assumed to pass. No minimum word count, mandatory section checklist or percentage grade is introduced.

This is a conservative extraction comparison, not semantic comprehension. Punctuation other than the significant tokens above is normalized. Geometric PDF reading order and unusual languages/layouts can require manual review. A passing result says that this parser recovered the expected visible text in order; it does not certify every third-party parser or the quality/truth of the resume.

## Private API and persistence

Both routes use the normal private/no-store `{data, requestId}` envelope:

| Method | Route | Behavior |
| --- | --- | --- |
| GET | `/api/v1/resume/:id/readability` | Current version plus a matching cached evaluation, or null. No rendering. |
| POST | `/api/v1/resume/:id/readability` | Strict `{expectedVersion}` only. Checks current saved snapshot or reuses its exact cached result. |

The server requires an authenticated personal owner and both `resume.read` and `resume.download`, because extracted text can include private contact fields. There is no new permission or shared-workspace access. Execution rechecks access/expiry; the API resolves the session again before returning private text. A transaction rechecks owner, deletion and revision after rendering and uses the existing advisory lock and atomic sanitized audit (`resume.updated`, reason `pdf_readability_checked`). No contact values or extracted text enter the audit.

`Resume.atsBreakdown.pdfReadability` retains one latest evaluation containing resume/version IDs, document hash, engine version, checkedAt, measured issues and page text. The hash includes the complete owner document; this result is private and is never used as an AI projection. Library/detail DTOs do not expose this metadata. Matching requires the current immutable version ID/number, document hash and `pdf-readability-v1` engine. Old/inconsistent data returns null. Content saves never rewrite the previous immutable snapshot; the next explicit check replaces only this latest derived result. Other ATS/tailoring metadata is preserved.

The shared schema bounds 30 pages, 200,000 extracted characters total, 1,200 expected text fragments and 64 grouped issues. Worker comparison caps source/extracted tokens at 50,000 each. Generated PDF size remains at most 15 MiB. Exports and checks share the existing two-worker pool; a full pool fails safely. A check has a 35-second worker deadline and 45-second browser/gateway POST timeout. No new service, dependency, migration, VM or subscription is added. Combined resume metadata remains capped at 2 MB; reaching it fails visibly without deleting other history.

Errors are sanitized: 401 session, 403 capability, 404 absent/foreign/deleted, 409 newer version, 413 request over 1 KiB, 422 invalid input, 503 worker/infrastructure unavailable. Failure never modifies resume content or saves a passing partial report.

## Verification

Automated service tests cover real Unicode/rich/multipage PDF extraction, hidden/empty content, duplicate occurrences, missing text, reordering, textless PDFs, pool limits, strict input, owner/permission/revision/deletion/expiry races, cache identity, metadata preservation, authentication and body limits. Frontend tests cover response identity/schema, sanitized errors and strict version requests. The component browser suite exercises the actual shared controls with synthetic transport, including all three viewport sizes, keyboard navigation, dirty/save behavior, cached results, retries, text escaping and long-preview scrolling.

On the signed-in native local stack, the existing synthetic `forge-quality-import-qa` resume produced a one-page passing result, displayed real extracted content and retained that result after a full reload at saved version 1. No provider call or content edit was made. Synthetic browser checks do not establish production VM capacity. Deployment and production verification remain separate release steps.
